# Bridge lifecycle (install, upgrade, uninstall)

The bridge itself is a DSH profile plugin. Its lifecycle is an operator action, not
part of task execution — a delegated worker never installs, upgrades, restarts or
uninstalls the bridge, because that reaches outside the task packet's authority and
affects every session on the host.

## Shape of an installation

- Package: `<profile>/node_modules/@local/dsh-codex-bridge-v1`
- Loader row: one `insert:` entry with id `dsh-codex-bridge-v1` in
  `<profile>/cordis.patch.yml`, pointing at that package.
- Installer state: `<profile>/node_modules/@local/.dsh-codex-bridge-v1/` holding
  `install-manifest.json` plus a `backups/` directory.
- Host entry: `dsh-host/index.cjs` inside the package (written by the project, not
  generated by the installer).

The installer never guesses a profile. Both the target profile and the package
source root are explicit arguments.

## Install

1. Plan first: `node scripts/install.mjs --profile <profile> --source <root> --dry-run`.
   The dry run validates and prints the full plan — files, exclusions, backup
   mappings, patch row — and writes nothing.
2. Validate: the source must contain `package.json`; the host entry is
   syntax-checked without being executed; symlinked content is refused; the tree is
   size-bounded.
3. Stage and copy: the source is copied through a staging snapshot into the package
   directory, with `.git`, `.runtime`, `.worktrees` and `evidence/raw` excluded.
   Pre-existing files that are replaced are backed up first.
4. Patch: exactly one owned insert row is appended, delimited by explicit start/end
   markers. Re-running the installer recognizes its own block and does not
   duplicate it; a foreign row with the same id is left untouched and reported.
5. Manifest: before/after SHA256 and the backup mapping are persisted.

## Uninstall

`node scripts/uninstall.mjs --profile <profile>` reads the manifest and:

- restores files whose content still matches what the installer wrote, from backup
  or by removing the file that did not exist before;
- reports a conflict and leaves the file alone when it was edited locally;
- preserves files it does not own, and removes directories only when they become
  empty;
- removes its own marker block from `cordis.patch.yml`, deleting that file only if
  the installer created it and nothing else is in it;
- refuses to act without a manifest, or with a manifest for a different profile.

`--dry-run` reports the same actions without changing anything.

## Identity upgrade (controller identity, `p0b-v1`)

Controller identity replaces the old top-level `token` / `credentialFile` /
`tokenEnv` authentication with per-controller credential files (`controllers`) and a
one-way task-store migration to `user_version = 1`. The endpoint is shared by every
controller, so this is a **whole-host maintenance action**, never a step inside a
coding task. Full schema, validation limits, audit and credential details:
[docs/controller-identity.md](../../../docs/controller-identity.md).

1. **Drain the whole host.** Finish or cancel every controller's tasks, collect and
   acknowledge results, and confirm a real true/0/0 stop. Do not restart with live
   tasks: recovery marks ambiguous work unknown and never replays it.
2. **Prepare.** Use a temporary upstream directory such as
   `F:/temp/agent-bridge-upstream` for backups, rehearsal and disposable tasks — never
   a git worktree. Use fake tokens in rehearsal; never read the machine's real
   credential files into a test or log. The deployment tooling prepares one token file
   per controller (creating missing files, validating and keeping existing ones) and
   generates an **overlap** host config that includes the temporary `legacy`
   administrator plus a **final** config that omits it; the deploy config's `identity`
   block carries `credentialDirectory`, `migrationBackupDirectory` and an optional
   `legacyTokenFile`. Its `controllers` + `identityMigrationBackupDirectory` output is
   an **identity fragment** to merge into the complete host config (keeping
   `dataDirectory`, `ownerId` and the other host fields), not a standalone config; the
   overlap and final configs are each complete. It also prepares one separate
   agent-peer config per root (shared `stateDir`, each with its own
   `bridge.credentialFile`), splitting any legacy single shared file. A dry run
   generates no token. Point each client at the overlap config for the window, with
   Claude's token in its root launch environment and Codex using its own credential
   file and peer config.
3. **Stop and back up** under the temporary directory: the installed package/manifest,
   both host configs, `<dataDirectory>` (`tasks.sqlite` including WAL/SHM because the
   events live there, and worktrees that matter), the client configs (Claude plugin,
   Codex `.mcp.json`, each root's agent-peer config and shared state) and the token
   files. The live controller token files are not disposable: keep them and their
   backups.
4. **Install the new package before the first restart.** Run the uninstall/install
   sequence (README install section) while the host is stopped. After installing, merge
   the overlap identity fragment into the complete host config used for the first
   restart. The first restart must load the identity-aware code that understands
   `controllers` and performs the store migration; never restart the old package with the
   new configuration.
5. **First restart (overlap).** Start with the overlap config. The store snapshots the
   old database into `identityMigrationBackupDirectory` and migrates 0 → 1; a mount
   failure (`STORE_BACKUP_FAILED` / `STORE_MIGRATION_FAILED`) means the host did not
   start and the old config can still be restored. Only the shipped v0 schema may
   migrate; only the shipped v1 schema may open as v1, and a version/shape mismatch is
   `STORE_SCHEMA_UNSUPPORTED`. Verify
   `bridge_capabilities.controllerIdentity` (`self`, `admin`, `controllers`) and that
   historical tasks stay readable (`bridge_list` with `submittedBy:null`). During the
   window `legacy` is an administrator for migration/repair only: every mutation of a
   foreign or **historical** task uses an explicit `override:{reason}`, recorded in the
   audit trail; do not use the legacy token for normal work.
6. **Dual-direction disposable-task smoke.** Submit a cheap read-only task from each
   root and check `submittedBy` (root `via:null`); run one disposable delegate in each
   direction (Claude → Codex and Codex → Claude) and confirm the delegate's tasks
   belong to the root principal with client-declared `via`; on Codex → Claude confirm
   the Claude delegate's strict MCP surface (only the plugin's two entries) and a cheap
   bridge call; on Claude → Codex confirm the delegate inherited the root
   identity/carrier and can submit, but do not claim Codex excludes other MCP servers;
   confirm a non-admin delegate cannot mutate the other root's task and that an admin
   credential is refused for delegation before spawn; then archive/clean or discard the
   disposable tasks deliberately.
7. **Second restart (final).** Remove the `legacy` entry and its token file; start with
   the final config (a v1 store is not migrated again). Verify the old legacy token now
   returns HTTP 401 `{"error":"unauthorized"}`, the remaining clients authenticate,
   and historical tasks are still readable (mutating them now needs a remaining
   administrator plus an override reason).
8. **Rollback is only a pre-work option.** The pre-migration snapshot plus the old
   package/config/clients can be restored **before any real new work exists**.
   Restoring it after new tasks/events/clients exist discards that work and leaves
   clients inconsistent with the identity; real tasks then require **forward repair**
   under the new schema, not a data rollback. Keep the snapshot and the live controller
   token files until the upgrade is accepted and real work has resumed; delete only
   intended test artifacts and, after the final restart, the temporary `legacy` token.

## Boundaries

- No global configuration is touched: not `~/.codex`, not `~/.agents`, not agent
  files, not tokens, not environment variables. The installer refuses those paths.
- No arbitrary recursive deletion: files are unlinked individually and directories
  are removed only when empty.
- Mounting takes effect on the next host start. Neither script restarts the host;
  never restart a live host as part of a task.
- Failures roll back: a run that fails after planning undoes what it wrote and
  reports what it could not undo.
- When a reinstall, upgrade or uninstall is genuinely part of the work, it is a
  separate, explicitly authorized operator task with its own evidence — not a step
  hidden inside a coding task.
